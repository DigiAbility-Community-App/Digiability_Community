3. INGRESS: new file communityapp/ingress.yaml   [DONE]
---------------------------------------------
Same pattern as the root ingress.yaml:
  - HTTP only redirects to HTTPS.
  - HTTPS adds HSTS (max-age=31536000; includeSubDomains, no preload).
  - /api/internal is NOT routed on the public chat host (admin reaches it
    in-cluster).
  - Traefik proxies WebSocket upgrades natively; no extra config needed.

---8<---------------------------------------------------------------------
# Public HTTPS entry point for the Digiability Community backend.
---
apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata:
  name: redirect-https
  namespace: communityapp
spec:
  redirectScheme:
    scheme: https
    permanent: true
---
apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata:
  name: hsts
  namespace: communityapp
spec:
  headers:
    stsSeconds: 31536000
    stsIncludeSubdomains: true
    forceSTSHeader: true
---
apiVersion: traefik.io/v1alpha1
kind: IngressRoute
metadata:
  name: communityapp-http
  namespace: communityapp
spec:
  entryPoints:
    - web
  routes:
    - match: "Host(`api.community.digiability.in`) || Host(`chat.community.digiability.in`) || Host(`forum.community.digiability.in`) || Host(`admin.community.digiability.in`)"
      kind: Rule
      middlewares:
        - name: redirect-https
      services:            # never reached; required by the CRD
        - name: user-svc
          port: 4001
---
apiVersion: traefik.io/v1alpha1
kind: IngressRoute
metadata:
  name: communityapp
  namespace: communityapp
spec:
  entryPoints:
    - websecure
  routes:
    - match: "Host(`api.community.digiability.in`)"
      kind: Rule
      middlewares: [{ name: hsts }]
      services: [{ name: user-svc, port: 4001 }]
    - match: "Host(`chat.community.digiability.in`) && !PathPrefix(`/api/internal`)"
      kind: Rule
      middlewares: [{ name: hsts }]
      services: [{ name: chat-svc, port: 4002 }]
    - match: "Host(`forum.community.digiability.in`)"
      kind: Rule
      middlewares: [{ name: hsts }]
      services: [{ name: forum-svc, port: 4003 }]
    - match: "Host(`admin.community.digiability.in`)"
      kind: Rule
      middlewares: [{ name: hsts }]
      services: [{ name: admin, port: 3001 }]
  tls:
    certResolver: letsencrypt
    domains:
      - main: api.community.digiability.in
        sans:
          - chat.community.digiability.in
          - forum.community.digiability.in
          - admin.community.digiability.in

7. FIREWALL on the VPS   [DONE — Hostinger firewall, 28 Sep]
----------------------
ufw is currently inactive. NOTE: "ufw deny 30000:32767" on its own does NOT
block NodePorts. kube-proxy redirects that traffic in nat PREROUTING, before
ufw's INPUT rules ever see it. The ClusterIP change in step 6 is what really
closes them; the raw-table drop below adds a second layer.

Allow SSH FIRST and keep the Hostinger browser console open in case of lockout.

  IFACE=$(ip route get 1.1.1.1 | awk '{for(i=1;i<=NF;i++) if($i=="dev") print $(i+1)}')

  ufw default deny incoming
  ufw default allow outgoing
  ufw allow 22/tcp
  ufw allow 80/tcp
  ufw allow 443/tcp
  ufw allow from 10.42.0.0/16 to any     # k3s pod CIDR (required by k3s with ufw)
  ufw allow from 10.43.0.0/16 to any     # k3s service CIDR
  ufw deny 30000:32767/tcp
  ufw deny 30000:32767/udp

  cp /etc/ufw/before.rules /etc/ufw/before.rules.bak
  cat > /tmp/raw.rules <<EOF
  *raw
  :PREROUTING ACCEPT [0:0]
  -A PREROUTING -i $IFACE -p tcp --dport 30000:32767 -j DROP
  -A PREROUTING -i $IFACE -p udp --dport 30000:32767 -j DROP
  COMMIT
  EOF
  cat /tmp/raw.rules /etc/ufw/before.rules.bak > /etc/ufw/before.rules

  ufw --force enable
  ufw status verbose
  iptables -t raw -S PREROUTING

Side effects:
  - 6443 (kube API) is no longer reachable from outside; kubectl over SSH still works.
  - Infisical NodePort 30080 closes. The operator uses ClusterIP; the UI is
    at https://infisical.digiability.in.
  - The CI "Sync ArgoCD" step only needs port 22, which stays open.

9. DATABASE GRANT for user-svc
------------------------------
The fix for VAPT M-002 (POST /api/auth/users/batch) makes user-svc read two
tables in the "chat" schema to check that the requester shares a conversation
with the users they look up:

  chat.conversation_members
  chat.conversations
  chat.group_invites

Locally every service uses the same Postgres role, so this just works. Please
check which role user-svc uses in prod (DATABASE_URL in Infisical /user-svc)
and, if it differs from chat-svc's role, grant read access:

  GRANT USAGE ON SCHEMA chat TO <user_svc_role>;
  GRANT SELECT ON chat.conversation_members, chat.conversations, chat.group_invites TO <user_svc_role>;

Without it, the endpoint returns a 500 after the next user-svc deploy.

11. CORS: NEW REQUIRED SECRET (replaces CLIENT_BASE_URL)

  ADD     CORS_ALLOWED_ORIGINS=https://community.digiability.in,https://admin.community.digiability.in

Rules the services enforce at startup when NODE_ENV=production (they exit
with a clear log message otherwise): comma-separated, exact https origins,
no "*", no paths, no CHANGE_ME / REPLACE / localhost / example values.
Requests from any other browser origin get no CORS headers. The mobile app
is not affected (native apps send no Origin).

12. ACCESS TOKEN LIFETIME
-------------------------
Access tokens now last 10 minutes. If /user-svc in Infisical sets
JWT_EXPIRES_IN, change it to 10m (or delete it — 10m is the default).

13. DATABASE GRANT for chat-svc
-------------------------------
chat-svc now checks, on every request and WebSocket connection, that the
user's login session is still active. Sessions live in user-svc's new table
public.sessions. If chat-svc uses a different Postgres role than user-svc:

  GRANT USAGE ON SCHEMA public TO <chat_svc_role>;
  GRANT SELECT ON public.sessions TO <chat_svc_role>;

forum-svc and user-svc already share the public schema — nothing needed.

14. REDIS FOR forum-svc (recommended)
-------------------------------------
Add REDIS_URL to /forum-svc in Infisical (same value as chat-svc's). With
it, a logout is enforced on the forum instantly; without it, the forum keeps
accepting a logged-out token for up to 15 seconds. Verified locally both ways.

15. DATABASE MIGRATION
----------------------
New user-svc migration: 20261002000000_add_sessions. It runs through the
existing `prisma migrate deploy` hook. Additive only: creates "sessions",
adds refresh_tokens."sessionId", and backfills one session per currently
logged-in device — nobody is logged out by it. No data is dropped.

16. PLACEHOLDER / WEAK SECRET SCAN
----------------------------------
Please run this on the VPS. It prints KEY NAMES only (never values) for any
secret in the communityapp namespace that is empty or still looks like a
placeholder:

  for s in $(kubectl -n communityapp get secret -o name | grep -v 'service-account\|ghcr\|infisical-machine'); do
    kubectl -n communityapp get $s -o json \
      | jq -r --arg s "$s" '.data | to_entries[]
          | select((.value|@base64d) | test("^$|CHANGE_ME|REPLACE|your[_-]|example|placeholder|localhost|127\\.0\\.0\\.1|changeme|xxx"; "i"))
          | "\($s)  \(.key)"'
  done

Known so far: CLIENT_BASE_URL=CHANGE_ME (item 11). Keys most worth checking
by eye, because the code has weak or empty fallbacks for them:
  - JWT_SECRET (admin)            must be long random, NOT the .env.example text

  - ADMIN_SEED_EMAIL / ADMIN_SEED_PASSWORD (admin)  should be unset once the

  - COOKIE_SECRET (user-svc)
  - MAIL_USER / MAIL_PASS / EMAIL_FROM / MAIL_HOST (user-svc)
  - USER_SVC_URL / CHAT_SVC_URL / FORUM_SVC_URL / NOTIF_SVC_URL  must be

  - NEXT_PUBLIC_APP_URL (admin)   should be https://admin.community.digiability.in
  - OPENAI_API_KEY / GOOGLE_VISION_API_KEY (moderation)
  - INCIDENT_WEBHOOK_URL / INCIDENT_ALERT_EMAIL
